# app.json

埋め込みアプリの設定ファイルです。`project/apps/<アプリ名>/app.json` に置きます。このファイルがあるフォルダだけを、Station はアプリとして扱います。アプリ名はフォルダ名で決まるので、`app.json` には書きません。

Station は起動したときに読みます。足したアプリや変えた `app.json` は、Station を再起動すると反映されます（アプリ管理の画面からの再読み込みは、あとで作ります）。

> [!WARNING]
> 下書きです。

## 例

```json
{
  "label": "Binette エディタ",
  "version": "0.1.0",
  "description": "ビネットを作り、編集し、プレビューする",
  "icon": "📝",
  "entry": "main.ts"
}
```

静的なアプリ（`panoplie/` だけ）なら、`entry` を書きません。

```json
{
  "label": "お知らせ"
}
```

## 欄

| 欄 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `label` | 文字列 | ○ | 表示名。前後の空白は除く。空にはできない。入口のアプリ一覧やアプリ管理の画面に出す |
| `version` | 文字列 | | アプリのバージョン（`1.2.3` の形を勧める）。アプリ管理の画面に出す |
| `description` | 文字列 | | 説明。アプリ管理の画面に出す |
| `icon` | 文字列 | | 一覧の行の先頭に出す文字（絵文字など）。入口のアプリ一覧の行に使う |
| `entry` | 文字列 | | 子プロセスで動かす module のパス。アプリのフォルダからの相対パスで、外へは出られない |

- `entry` に書けるのは、`/` 区切りの相対パスです。絶対パス、`..`、`\`、制御文字は使えません。実在するファイルでなければなりません。アプリのフォルダにはシンボリックリンクを置けないので、リンクでフォルダの外を指すことはできません。
- `entry` の module の default export を、`fetch(req: Request) => Response | Promise<Response>` を持つオブジェクト（`export default { fetch(req) { … } }`）にします。関数を直接 default export する書き方（`export default (req) => …`）も使えます。`fetch` を持たないと、起動に失敗します。
- `entry` と `panoplie/` のどちらも無いアプリは、異常として扱い、起動しません。
- 知らない欄は無視します。
- `app.json` は 64 KiB までです。形式が正しくないとき（JSON として読めない、`label` が無い、など）は、そのアプリを異常として扱い、理由を日本語で記録します（アプリ管理の画面に出す）。ほかのアプリには影響しません。
- アプリ名の規則に合わないフォルダや、予約名のフォルダは、アプリになりません（予約名で `app.json` があるものは、理由つきの異常として扱い、入口のアプリ一覧には出しません）。規則は [spec.md](spec.md) の「アプリ名」を参照してください。

## アプリのフォルダ

```
apps/<アプリ名>/
├── app.json
├── main.ts       # entry に書いたもの（任意）
└── panoplie/     # 静的な .bina とファイル（任意）
```

| `entry` | `panoplie/` | 動き |
| --- | --- | --- |
| あり | なし | 子プロセスに渡す |
| なし | あり | Station が `@binette/coulisses` で直接配る。子プロセスは起動しない。GET と HEAD だけ（他は 405） |
| あり | あり | まず子プロセスに渡す。GET と HEAD で 404 が返ったときだけ `panoplie/` から探す |

- **アプリのフォルダ（`panoplie/` や `entry` を含む）の中に、シンボリックリンクは置けません。** 1 つでもあると、そのアプリは異常になり、起動しません。Deno のパスの権限はリンクの先を解決せずに判定するため、リンクがあると、権限の外のファイル（Station のデータベースなど）を読めてしまうからです。`git clone` や `tar` で入ったリンクも同じです。データフォルダ `data/apps/<アプリ名>/` も同じで、リンクがあれば起動しません。
- `panoplie/` の中の `.bina` が不正だと、そのアプリは異常になります。`panoplie/` の中のファイルは 1 MiB までです（ET で運べる本文の上限。超えるファイルがあると、そのアプリは異常になります）。
- フォルダのパスに `,` を含めることはできません（子プロセスの権限指定が区切りと混ざるため、起動せずに異常にします）。

## 子プロセスの権限

子プロセスは、Deno の権限を絞って起動します。ほかのファイル、ネットワーク、環境変数、サブプロセスは使えません。

> [!IMPORTANT]
> Deno の権限は、ローカルのファイルの `import`（`with { type: "text" }` や JSON）を止めません。アプリは `import` で `--allow-read` の外のファイルを読めてしまいます。埋め込みアプリは、実装者が自分で置く信頼できるコードとして扱います（[spec.md](spec.md) の「埋め込みアプリの信頼」）。

| 権限 | 範囲 |
| --- | --- |
| `--allow-env` | `EBINA_PORT`、`EBINA_APP_TOKEN`、`EBINA_DATA_DIR` だけ |
| `--allow-net` | `127.0.0.1:<EBINA_PORT>` だけ（外部への通信はできない） |
| `--allow-read` | アプリのフォルダ `apps/<アプリ名>/` と、データフォルダ `data/apps/<アプリ名>/` |
| `--allow-write` | データフォルダ `data/apps/<アプリ名>/` だけ（アプリのフォルダには書けない） |
| `--allow-run`、`--allow-ffi` など | なし |

- `--no-prompt` で起動するので、足りない権限を後から求めても許可されず、エラーになります。
- モジュールの解決には Station の `deno.json` を使います（`--config`）。`imports` に書いてある `hono` などは、そのまま `import` できます。アプリのフォルダの `deno.json` は読みません。
- 子プロセスは、モジュールを取得しません（`--cached-only`）。`deno.lock` も書き換えません（`--frozen`）。使えるのは、Station の `deno.json` の `imports` にあり、`deno.lock` とキャッシュに入っている依存だけです。ほかの `npm:`・`jsr:`・URL の `import` は、起動に失敗します。アプリだけが使う依存は、Station の `deno.json` の `imports` に足し、`deno install` で `deno.lock` とキャッシュに入れてから、Station を再起動します。
- 取得しないので、プロキシや独自 CA の環境変数（`HTTPS_PROXY`、`DENO_CERT` など）は子プロセスに渡しません。

## 子プロセスに渡すもの

| 環境変数 | 内容 |
| --- | --- |
| `EBINA_PORT` | 待ち受けるポート（`127.0.0.1`）。起動のたびに OS が選ぶ |
| `EBINA_APP_TOKEN` | Station からのリクエストを確かめる秘密。起動のたびに作り直す |
| `EBINA_DATA_DIR` | データフォルダ `data/apps/<アプリ名>/` の絶対パス。起動前に Station が作る |

- Station の環境変数は引き継ぎません。上の 3 つのほかに、Deno が動くのに要る `HOME`、`DENO_DIR`、`XDG_CACHE_HOME`、`PATH`（Station にあれば）だけを渡します。ただし、アプリが読める環境変数は上の 3 つだけです。
- 標準出力と標準エラーは Station が行ごとに受け取り、Station のログにも出します（標準エラーは警告）。`EBINA_APP_TOKEN` と同じ文字列が出力に入っていたら、記録にもログにも `(token)` に置き換えて残します。待ち受けの開始を知らせる `EBINA_READY` の行は、Station の runner が出します。アプリが同じ行を出しても、Station は runner への確認（`Ebina-Runner-Probe` ヘッダー付きのリクエスト。runner が答え、アプリには渡さない）が通るまで起動済みにしません。

## アプリが実装するものと、運び方

アプリが実装するのは `fetch(Request) → Response` だけです。待ち受けと `Ebina-App-Token` の確認は、Station が用意する `runner/runner.ts` が行います。

- `Ebina-App-Token` が一致しないリクエストは、runner が 403 `{"error":{"code":"forbidden"}}` で断り、アプリには渡しません。比較は時間をかけない方法（timing safe）で行います。
- アプリの `fetch` が例外を投げた、または `Response` 以外を返したときは、runner が 500 `{"error":{"code":"internal_error"}}` を返します。理由は標準エラーにだけ出します（Station のログには出ます）。
- アプリが返した 401 は、そのままクライアントに届きます。Station が自分のセッション切れで返す 401 には `Ebina-Station-Error: unauthorized` が付き、ebina-front はこのヘッダーがあるときだけログイン画面へ戻ります。アプリの応答の `ebina-` で始まるヘッダーは中継で除くので、アプリはこの印を付けられません。
- アプリが受け取る `Request` の URL は、`http://127.0.0.1:<ポート>` を基点にした、アプリの中のパスです。`Ebina-User` にログイン中のユーザー ID が入っています。ヘッダーの規則は [spec.md](spec.md) の「アプリへの中継」を参照してください。

Station とのあいだは、今は `127.0.0.1` の HTTP で運んでいます。これは Station の内部のことで、アプリのコードは HTTP を意識しなくて構いません（あとで運び方が変わることがあります）。
